# ADR-005 — Migrations finais e seed

**Status:** Aceita
**Fase:** 4
**Data:** 2026-11-26

---

## 1. Contexto

O Registry é um projeto acadêmico reiniciado na Fase 4. Não há dados de produção a migrar nem histórico de schema a preservar.

O banco precisa nascer já no estado final, com:

- tabelas, colunas, constraints e índices corretos;
- unicidade apenas entre registros ativos;
- soft delete e auditoria;
- seed de demonstração com UUIDs fixos;
- reprodutibilidade total em qualquer máquina.

---

## 2. Decisão

Adotar **uma migration final por tabela**, sem migrations de correção durante a fase acadêmica.

### Ordem das migrations

| Ordem | Arquivo | Conteúdo |
|---|---|---|
| 1 | `V1__create_clientes.sql` | Tabela `clientes`, índices e unique parcial de CPF ativo |
| 2 | `V2__create_veiculos.sql` | Tabela `veiculos`, FK para `clientes(uuid)`, unique parcial de placa ativa |
| 3 | `V3__create_pecas.sql` | Catálogo de peças (sem estoque) |
| 4 | `V4__create_servicos.sql` | Catálogo de serviços |
| 5 | `V5__seed_dados_iniciais.sql` | Seed com UUIDs fixos |

### Regras

1. `BIGINT GENERATED BY DEFAULT AS IDENTITY` como PK interna.
2. `UUID` único exposto na API.
3. `TIMESTAMP` sem timezone, seguindo o padrão do monólito.
4. `NUMERIC(12,2)` para valores monetários.
5. Constraints e índices nomeados explicitamente.
6. Unique parcial para campos únicos entre ativos:

   ```sql
   CREATE UNIQUE INDEX ux_veiculos_placa_active
       ON veiculos (placa)
       WHERE is_active = TRUE AND deleted_at IS NULL;
   ```

7. Seed com `ON CONFLICT DO NOTHING` e `created_by = 'SEED'`.
8. Inserir cliente antes do veículo (FK).
9. **Nenhum campo de estoque** em `pecas`.

### Alterações de schema

Durante a fase acadêmica, uma alteração de schema deve ser feita **na migration original** e o volume local recriado:

```bash
docker compose down -v
docker compose up -d --build
```

Não criar `V6__fix_...` para corrigir algo que ainda não foi entregue.

---

## 3. Consequências

### Positivas

1. **Schema final legível**: cada tabela tem uma única fonte de verdade.
2. **Ambiente reproduzível**: `down -v` + `up` recria tudo do zero.
3. **Sem dívida de migrations** de correção em um projeto sem produção.
4. **Seed determinístico** com UUIDs fixos para Postman/Newman e testes E2E.
5. **Soft delete compatível** com reutilização de CPF/placa/código após desativação.

### Negativas / custos

1. **Não serve para produção real** com dados históricos.
2. **Alterações exigem reset** do volume local.
3. **Índices parciais não são criados pelo Hibernate** nos testes com H2; a validação completa depende de PostgreSQL.

### Mitigações

- Documentar a regra de reset em `docs/03-modelo-de-dados.md` e `README.md`.
- Validar migrations em PostgreSQL real no ambiente Docker e no PR.
- Manter os testes de repositório/REST cobrindo as regras de unicidade e soft delete.

---

## 4. Alternativas consideradas

### Alternativa A — Migrations incrementais com correções (rejeitada)

- Histórico completo de evolução.
- Necessário em produção, mas gera ruído em um projeto acadêmico sem dados.
- **Motivo da rejeição:** o schema ainda está sendo definido; correções devem entrar na migration original.

### Alternativa B — `hibernate.hbm2ddl.auto=update` (rejeitada)

- Schema gerado automaticamente pelas entidades.
- Não versiona constraints/índices parciais e pode divergir entre ambientes.
- **Motivo da rejeição:** perda de controle e de reprodutibilidade.

### Alternativa C — Seed via código/aplicação (rejeitada)

- Poderia usar um `CommandLineRunner`/startup bean.
- Executaria em todos os ambientes e exigiria idempotência em código.
- **Motivo da rejeição:** o seed é dado de demonstração e pertence ao banco/migration.
